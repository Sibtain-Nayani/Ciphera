# Ciphera v3 Production Remediation Roadmap

**Status:** Active
**Baseline:** `sibtain` at merge `6be39af` (2026-11-04)
**Scope:** v3 runtime, deployment, documentation, and tests only. `Ciphera/` and `CipheraV2/` are historical prototypes and must not become v3 imports, package dependencies, build contexts, or runtime data sources.

This roadmap turns the findings from the 2026-11-03 repository review and the post-merge check into individually verifiable work. Do not mark an item done because code compiles: its acceptance checks must pass. Keep each fix small, add the regression check with the fix, run the relevant checks, record the result, then start the next item.

## Working rules

1. Work only in `v3/`. Do not copy source or configuration from either prototype into a runtime or build path.
2. Fix one finding at a time. Avoid bundling adjacent refactors unless the current finding cannot be fixed safely without them.
3. For each finding, add a regression test that fails before the fix. Run that test, the closest existing suite, and relevant type/build checks. Record the exact command and result in the change.
4. Use disposable databases and synthetic documents in tests. Never run destructive migration checks against production or a developer's working database.
5. Preserve tenant ownership and audit history during migrations. If existing shared-org records cannot be assigned safely, stop and produce a reviewed mapping instead of guessing.
6. Use one source of truth for each concern: one identity model, one PostgreSQL schema/migration history, one document-release path, and one policy/verifier contract.

### Supabase implementation notes

The database migration should not expose Postgres directly to the browser as a shortcut around the current authorization model. Keep database credentials and any Supabase secret/service-role key server-side; Supabase documents that elevated secret/service-role access bypasses RLS. If RLS is part of the design, enable it and set grants explicitly for each exposed table, write allow/deny tests, and verify that pooled connections cannot leak tenant context. For persistent FastAPI/Celery containers, use the Supabase dashboard's direct or session-pooled connection details based on network support; transaction pooling has session-feature limitations and is aimed at short-lived connections. See [Supabase connection guidance](https://supabase.com/docs/guides/database/connecting-to-postgres), [pooling limits](https://supabase.com/docs/guides/database/connecting-to-postgres/pooling-and-limits), and [RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security).

## Release gates and target metrics

The prior review's qualitative starting estimates remain **Security 2/10, Reliability/observability 3/10, Scalability 3/10, Code quality 4/10, Test coverage 3/10**. They are not measured coverage percentages.

Do not launch publicly until every P0 is closed. Initial targets:

- **Security: 8/10.** No open P0s; all protected route/tenant combinations have allow/deny tests; no default secrets; critical/high dependency findings are patched or formally time-bounded; release verification is independent and format-aware.
- **Reliability/observability: 7/10.** Every request/job has a correlation ID; alerts cover API errors, worker failures, queue age, and DB health; define pilot SLOs and RPO/RTO; demonstrate restore and retry recovery.
- **Scalability: 6–7/10 for pilot.** API instances are stateless, files are in shared storage, workers scale independently, DB pools are capped, and a 2× pilot-peak load test passes with resource headroom.
- **Code quality: 7/10.** Clean CI, no ignored TypeScript/build errors, no lint errors, clear module/config boundaries, one auth and persistence path.
- **Test coverage: 7/10.** At least 80% line coverage for core authorization, document lifecycle, and redaction decision logic, plus explicit security, failure-injection, format, and end-to-end tests. Coverage is necessary but not proof of safe redaction.
